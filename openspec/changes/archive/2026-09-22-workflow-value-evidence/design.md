# Design: workflow value evidence

## Decision

The proof program will use a small workflow-evidence record before implementing
a companion. It joins deterministic benchmark findings to a testable product
hypothesis without mistaking a public repository for user research. The record
has five parts: source finding, intended operator and mobile context, bounded
workflow and desktop remainder, observable success/friction measure, and the
reason native UI is preferable to the viable alternative or a recorded decision
not to proceed.

Practitioner feedback is optional evidence, not a prerequisite for reading a
public benchmark. When sought, it must use a consented, minimal question set and
record only synthesized findings. It must not solicit credentials, sensitive
customer data, or an implied commitment.

## Alternatives considered

- Treat a source route or screen count as workflow value: rejected because it
  establishes structure, not user pain or a mobile advantage.
- Require a formal study before any fixture: rejected because it would prevent
  early technical proof. A documented unvalidated hypothesis remains allowed but
  cannot be presented as validated demand.
- Declare native UI the default winner: rejected because a PWA or WebView can be
  the honest recommendation for a particular workflow.

## Contract change

No shared software contract changes. This proposal adds an evidence and decision
record, not a new App Graph node, public CLI field, or runtime API.
