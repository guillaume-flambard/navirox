## Context

`navirox migrate` moved one unit of the pilot, and the report named the two imports
it did not carry. That report is where the previous change stopped. A migration is
only worth something if the moved code runs, and the pilot has never been run
anywhere except a browser.

Two facts shape this change. The native runtime has no router, so the pilot's three
routes cannot be reproduced as routes. The native API surface has no generic
key/value storage, so the browser's `localStorage` has no direct counterpart. Both
are recorded as gaps rather than worked around silently.

The migration output is the input. The pilot application is assembled around the
file the CLI wrote, and the file is not edited: if the journey needed the store
changed, the migration would have failed and this change would say so.

## Goals / Non-Goals

**Goals:**

- Show that the unit the migration moved runs in a native application on both
  platforms.
- Exercise the pilot's journey end to end: list, favourite, count, favourites view,
  one detail, and a favourite that survives a relaunch.
- Put the platform specific step through the native API seam instead of dropping it.
- Record every file written by hand and why the run could not write it.
- Keep the canary and every existing gate green.

**Non-Goals:**

- Changing any package under `packages/*`. This change adds an application.
- A runtime router. The pilot's routes become one view switch and the difference is
  recorded.
- A generic key/value storage module. The favourites module is adapted to the secure
  store that exists.
- Wiring the pilot journey into CI. That belongs to the installable release.
- Making the application installable from a registry. As a workspace member it
  consumes the packages through `workspace:*`.

## Decisions

**The pilot application is generated by the documented scaffold and then filled by
the shipped migration.** `examples/vue-pilot` starts as `create-navirox` output, so
the path a user takes is the path that is exercised. The scaffold writes `link:`
dependencies because it finds this checkout; as a workspace member the manifest is
changed back to `workspace:*`, and the template's nested `pnpm-workspace.yaml` is
removed so the root workspace owns the install. Alternative rejected: a hand-written
app, which would prove the runtime again rather than the migration.

**The moved store is imported where the run put it.** The migration writes
`src/stores/catalogue.ts`, so the application imports that path. The file is not
moved to the canary's root-level `stores/` layout, because the point is that the
application consumes the run's output at the run's path. Alternative rejected:
reshaping the output by hand, which would hide the path convention the CLI chose.

**The two unresolved imports become the two hand-written modules, and nothing else.**
The store imports `../api/products` and `../lib/favourites`. Both are adaptable, so
the run reports them. On native, the API client's static asset read becomes a
bundled product list, and the favourites module's `window.localStorage` becomes the
secure store from `@memolabs-apps/native`. Alternative rejected: keeping favourites
in memory, which would pass the list and the count but would not exercise the native
API seam and would not survive the relaunch.

**The journeys are two Detox specs with shared conventions and separate app
identities.** The pilot spec drives the pilot's testIDs; the canary spec is left
untouched. Both are run from the same machine, and the canary run is the
non-regression check. Alternative rejected: extending the canary spec with the pilot
journey, which would couple two applications that fail for different reasons.

Contract change questions, per AGENT-GUIDE section 12: this change touches no shared
contract. No package under `packages/*` changes, no App Graph concept is added, no
schema version moves, and no public type or component surface is altered. The four
questions therefore do not apply, and the two decisions that would have raised them
(the missing router, the missing key/value storage) are explicitly out of scope and
recorded as gaps in the evidence report.

## Risks / Trade-offs

- **A workspace member can disturb the root gates.** `examples/*` is a workspace
  glob, so the application joins `turbo run build`, the root install and
  `deps:check`. The mitigation is to keep its dependency versions aligned with the
  canary, which already passes those gates, and to run the full gate set before
  landing.
- **Two native applications on one machine.** The Detox configurations name a
  simulator and an AVD; the pilot uses its own values and its own bundle identity,
  and the canary keeps the values it has. A run of one must not leave a Metro or a
  simulator that breaks the other, so the journeys are run in sequence.
- **The relaunch assertion is the fragile one.** A secure store write is
  asynchronous and the journey asserts persistence across a relaunch, which depends
  on the provider rather than the store seam. If it proves flaky, the honest fallback
  is to assert persistence across a view switch and record the relaunch gap, not to
  drop the assertion silently.
- **The migration is not re-run by CI.** The app carries the file the CLI wrote at
  the recorded revision, and the evidence report records that revision. A later CLI
  change can make the file stale, which is exactly what the revision record is for.

- Whether the web pilot's router gap should be closed by the 0.2 router or by an
