## 1. Declare the tolerance

- [x] 1.1 Add the optional `tolerance` to the scenario contract and its validator in `packages/visual-benchmark/src/scenario.ts`: a maximum relative grid difference and the test identifiers the scenario requires. Verify `pnpm --filter @memolabs-apps/visual-benchmark build` exits 0 and `pnpm --filter @memolabs-apps/visual-benchmark test` passes.

  `packages/visual-benchmark/src/scenario.ts` exports `ScenarioTolerance { gridSize: number; identifiers: string[] }` (gridSize is the maximum relative difference between the two normalized grid sizes, as a fraction of the larger side), `VisualScenario` carries `tolerance?: ScenarioTolerance`, and `validateScenario` calls the new `checkTolerance` after `checkMotion`. ## 3. The verdict

- [x] 3.1 Add the tolerance evaluation to `packages/visual-benchmark/src/tolerance.ts`: every declared capture present on both platforms, the normalized grids within the declared relative difference, the identifiers found on both platforms, and the motion labels in order. Verify unit tests for a pass, a grid outside the tolerance, a missing capture and a missing identifier.

  `evaluateTolerance(run: ToleranceRun): ToleranceVerdict` evaluates the four checks (`captures`, `grid`, `identifiers`, and `motion` only when the scenario declares it) and returns `{ scenario, verdict, checks, decidedBy? }` where `decidedBy` names the check that decided a failure. The grid check compares the normalized widths and heights and takes the largest relative difference against `tolerance.gridSize`, and the pixel difference ratio is deliberately not a check. Six tests in `src/tolerance.test.ts` cover a pass (with the grid detail naming the accepted 2.54 percent), a grid outside the tolerance, a missing capture (`rest.android`), a missing identifier (`records-list.android`), motion labels out of order, and a scenario that declares no motion. `pnpm --filter @memolabs-apps/visual-benchmark build` exits 0 and `pnpm --filter @memolabs-apps/visual-benchmark test` passes 78 tests in 7 files.
- [x] 3.2 Record the verdict in the capture run: `packages/visual-benchmark/scripts/capture-records-native.mjs` evaluates the declared tolerance, prints the verdict and its checks, writes them into the evidence report, and exits nonzero on a failed verdict. Verify a real iOS run reports `pass` and the evidence file names every check.

  The script reads the two captures of each declared capture back through `normalizeImage(decodePng(...))`, builds the evaluation input (`platforms: [platform]`, one `captures` entry per declared capture, one `identifiers` entry per declared identifier, and `motion` only when the scenario declares it), calls `evaluateTolerance`, prints `Verdict: <pass|fail>` plus one `  <pass|fail> <name>: <detail>` line per check, writes `tolerance` and `verdict` into the evidence JSON, and pushes a failure for a failed verdict so the run exits nonzero. The real run `node packages/visual-benchmark/scripts/capture-records-native.mjs --platform ios --workspace /tmp/navirox-tolerance4` exits 0 and reports pass for both scenarios: `pass captures` (1 and 5 declared captures exist on the web and on ios), `pass grid` (largest grid difference 0.00 percent, inside the declared 5.00 percent), `pass identifiers` (all 4 declared identifiers were asserted on the web and on ios), and, for the motion scenario, `pass motion` (the labels in the required order). The failure path was also observed for real: an earlier revision read the decoders from a scope they were not imported into, so the run printed `Verdict: fail` / `fail grid: no capture had both sides decoded` and exited 1, which is the designed behaviour for a failed verdict; passing the decoders into the grid helper fixed it.
