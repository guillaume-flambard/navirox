This records the first time the source seam faced a web application that was
written for the browser rather than for Native. It is the evidence for issue
#12, and the input the next issue needs to choose a migration slice.

## The pilot and how to reproduce it

The pilot is a Vue 3 + Vite application generated by a pinned scaffolder, kept
in the repository at `pilots/vue-web`. It is a non-member of the pnpm workspace
on purpose: `pnpm-workspace.yaml` lists `examples/*` as a member glob, so a
generated Vite app placed there would be pulled into `turbo run build`, the
workspace install and `syncpack`, none of which it participates in. `pilots/`
sits outside both member globs, so the root gates are untouched. This is a
deliberate deviation from the issue's option text, which proposed
`examples/pilot-web-vue`.

Reproducible setup:

```
cd pilots
corepack pnpm dlx create-vue@3.24.0 --ts --router --pinia vue-web
cd vue-web
corepack pnpm install --ignore-workspace
corepack pnpm run build
```

`--ignore-workspace` is required for the same reason: without it pnpm resolves
the repository's root workspace and the pilot never gets its own `node_modules`.
The build passes locally (`vue-tsc --build` then `vite build`, 39 modules, lazy
chunks for the two non-home routes), so the project is a valid inspection
subject. The pinned generator version, the added files and the journey are also
recorded in `pilots/vue-web/README.md`.

### The acceptance journey

One journey, chosen to exercise routing, shared state and a browser-only
capability together:

1. `/` loads the catalogue (`fetch` of `/api/products.json` through Pinia) and
   lists five products.
2. Toggling a product's favourite updates a count in the application header.
3. `/favourites` lists the favourites, backed by `localStorage`, not the store.
4. Selecting a product name opens `/product/:id` and shows that product.

The source shape: `src/router/index.ts` declares three routes, one eager and two
lazy; `src/stores/catalogue.ts` is a Pinia setup store; `src/api/products.ts` is
a `fetch` client; `src/lib/favourites.ts` reads and writes `localStorage`;
`src/App.vue` and `src/views/*.vue` are four single file components.

## Commission

### Missed units

`src/main.ts` and `src/router/index.ts` are real modules the application cannot
run without, and neither is a unit. `src/main.ts` is the entry point that
installs Pinia and the router; `src/router/index.ts` is the module that names
all three routes. The graph therefore models the four components and the
business logic but not the wiring that makes them an application.

### Routes

The application has three visible routes. The graph has `routes: []` and
`findings: router-not-extracted`, whose own message is honest about why: the
adapter does not read a router module. Route extent is unknown, so the plan
cannot tell a component-navigation unit from a dead one.

### Missing edges

The graph's `edges` array holds exactly three entries, all `uses` edges from a
utility to its own capability. There is no edge from a view to the store, from
the store to the API client, or from the store to the favourites module. The
dependency information that exists is intra-file. The store's `import` of
`fetchProducts` and `useFavourites` (`catalogue.ts:3-4`) is invisible.

### Browser and server boundaries

Two browser-only boundaries are captured correctly as capabilities:

- `fetch` in `src/api/products.ts:8` (`network-request:invoke`).
- `localStorage` read at `src/lib/favourites.ts:7` and write at line 25.

The API client fetches a static JSON file from the app origin, so the only
server boundary is a static asset, not an authenticated backend. That is fine
for a pilot and is stated here so no one reads the `network-request` capability
as evidence that Navirox handles a real API.

### Dependency unknowns

`vue`, `pinia` and `vue-router` are the only dependencies found. `vue` and
`pinia` are `portable` because the compatibility registry carries a record.
`vue-router` is `unknown`: a routing library's behavior on a native surface is
the exact question route extraction leaves open, and no record answers it.

### Was anything wrongly called safe to share?

No. `shared` is 0, so the plan made no "safe to share" determination at all. The
risk this check looks for, a unit classified `shared` whose implementation is
actually browser bound, does not arise here because nothing was classified
`shared`. The one browser-bound pair (`localStorage`) and the network client were
classified `adaptable`, not `shared`.

That absence is itself the finding, and it is the single most important result
for the next issue: the only migration transform that exists today copies units
classified `shared`, and this pilot has none, so **the current transform would
copy nothing.** See the slice below.

## Classification spot check

| Subject | Classification | Reason it is right or wrong |
| --- | --- | --- |
| `pinia` dependency | portable | Store shape survives the seam; the acceptance app already runs a Pinia store on both platforms. |
| `vue` dependency | portable | Same. |
| `vue-router` dependency | unknown | Correct to refuse; route extraction did not happen. |
| `src/stores/catalogue.ts` | portable | Correct: it is business logic with no browser call of its own. |
| `src/api/products.ts` utility | adaptable | Correct: `fetch` is a browser call that must change. |
| `src/lib/favourites.ts` utility | adaptable | Correct: `localStorage` must become a native storage call. |
| `App.vue`, three views | native-replacement | Correct: the blueprint rewrites the view layer. |

No classification in this run is wrong on inspection. The two that could mislead
are `portable` on the store and `adaptable` on the utilities, because both carry
an import of a unit that does not move unchanged. The plan says what a unit is,
not whether the file it copies will resolve after it moves; that is a transform
concern and belongs to the slice.

## The smallest migration slice for #13

The slice has to be producible today. The plan offers `portable` units, and the
one transform copies `shared` units, of which there are none. Two honest options:

1. **Generalize the copy predicate** from `shared` to `shared` plus `portable`
   (the plan's own words: a portable unit "moves with its shape intact"), then
   run it on the pilot. Bounded, framework-neutral, and testable.
2. **Add a new transform** for portable units next to the existing one. Same
   effect, more surface.

Recommendation: option 1, because it changes one predicate and one test, and it
gives the pilot a real output without inventing a target-specific transform.

The slice, concretely:

- The migration engine moves units the plan classifies `shared` or `portable`,
  keeping the current byte-for-byte, same-relative-path behavior and the current
  dry-run, state file and idempotence guarantees.
- Applying it to `pilots/vue-web` moves `src/stores/catalogue.ts` and the two
  dependency declarations (`vue`, `pinia`). `vue-router` stays `unknown` and is
  not moved.
- The run reports, per moved unit, every dependency the plan classified
  `adaptable` and therefore did not move: `src/api/products.ts` and
  `src/lib/favourites.ts` for the store. That report is the manual work list.

What must stay manual:

- The four components and their native navigation implementation. The route
  paths are now inspected, but a native screen and navigator are still hand
  work.
- The two adaptable modules. `localStorage` becomes a native storage call and
  `fetch` becomes the native API client; neither is a copy.
- The app bootstrap and router. Neither is a unit today.

Native acceptance criteria, for #13:

- The migrated native pilot boots on iOS and Android.
- The catalogue list renders from a store that reached the native app through
  the migration, not through hand-copying.
- Toggling a favourite updates the header count and survives navigation, with
  the value in native storage rather than `localStorage`.
- The migrate command run that produced it is idempotent and leaves a readable
  record.

## Gaps carried forward

Bounded follow-up work, not new source frameworks:

- Route-to-screen and nested-route modelling: literal top-level paths are read;
  component targets and nested routes remain deliberately unresolved.
- Application modules as units: `main.ts` and `router/index.ts` are invisible.
- Cross-unit dependency edges: a view's import of a store, and a store's import
  of a utility, are not modelled.
- A compatibility record for `vue-router`.
- A transform that can move a portable unit whose imports are adaptable, or a
  report that makes the unresolved imports explicit (this slice).
